तपाईंको TV — COMPLETE IPTV / LIVE TV WEB APPLICATION DEVELOPMENT PROMPT

PROJECT OVERVIEW

Act as a senior full-stack engineer, streaming-platform architect,
security engineer, and product-focused UI/UX designer.

Build a complete, production-ready, responsive IPTV and Live TV web
application named:

    तपाईंको TV
    Your Television, Everywhere.

The application should provide a simple way for anyone to discover and
watch publicly available, properly licensed live television streams. It
should support Nepali channels, sports, news, entertainment, movies,
music, regional channels, and international channels where available.

The most important product rule is:

    VIEWERS NEVER NEED TO LOG IN.
    ONLY AUTHORIZED ADMINISTRATORS NEED TO LOG IN.

Do not build a generic AI-generated dashboard. Do not use excessive
gradients, random decorative icons, huge rounded cards everywhere,
unnecessary glassmorphism, glowing neon effects, fake statistics,
placeholder content presented as real, or animations that make the
interface feel artificial. The product must feel like a carefully
designed, premium, minimalist streaming service.

Build the actual working application, not merely a visual mockup. Do not
claim a feature is functional until it is implemented and connected to
its data source.

===================================================================== 1.
PRODUCT PRINCIPLES AND USER ACCESS
=====================================================================

1.1 Public viewer access — absolutely no login - Anyone can open the
website and start browsing immediately. - Do not create viewer
registration, sign-up, login, OTP, phone verification, email
verification, membership, or subscription screens. - Do not require an
account to watch a channel. - Homepage, channel listings, categories,
search, event pages, and the player must be publicly accessible. -
Public viewers can browse and watch available streams without
authentication. - Store favorites, recently watched channels, and simple
viewing preferences locally in the browser using localStorage. - If
local storage is unavailable, the application should still work without
those optional features. - Do not block the player behind a login
wall. - Do not show a login prompt to ordinary viewers.

1.2 Administrator access — login required - Create a separate admin area
at /admin. - Create the admin login page at /admin/login. - Only
authorized administrators can access admin routes and perform write
operations. - Do not provide public admin registration. - Admin accounts
must be provisioned through a trusted, secure process. - After
successful login, redirect the administrator to /admin/dashboard. -
Include a logout option. - If an administrator is not authenticated,
redirect them to /admin/login. - Verify authorization on the backend and
through Firebase Security Rules. Hiding admin buttons in the frontend is
not security.

1.3 Two access types only

PUBLIC VIEWER: - No login or registration. - Browse channels and
categories. - Search channels and events. - Watch available streams. -
View featured events and announcements. - Save favorites locally. - View
recently watched channels locally. - Share channel and event links.

ADMINISTRATOR: - Secure login required. - Manage channels and stream
URLs. - Manage featured events and priority. - Upload banners and
channel logos. - Manage categories and homepage content. - Publish
announcements. - Configure application settings. - Review channel status
and content.

===================================================================== 2.
DESIGN SYSTEM AND VISUAL IDENTITY
=====================================================================

Create a premium, minimalist, modern streaming interface.

Brand: - Name: तपाईंको TV - English tagline: Your Television,
Everywhere. - Use a simple, recognizable TV-inspired logo. Do not create
an overly complicated mascot or abstract AI-looking symbol. - Support
Nepali and English text properly.

Visual direction: - Default theme: dark. - Background: near-black or
deep charcoal, such as #101114. - Surface colors: subtle dark grey, such
as #191B20 and #22252B. - Text: clear white and soft grey. - Accent:
restrained red or warm coral for LIVE indicators and primary actions. -
Use green only when it has a meaningful status purpose, such as an
available/online indicator. - Use a clean font pairing with Noto Sans
Devanagari for Nepali and a modern sans-serif for English. - Use
consistent spacing, alignment, typography, and component sizes. - Use
subtle borders and restrained shadows. - Avoid excessive gradients,
neon, glassmorphism, visual clutter, oversized typography, and
unnecessary motion. - Use real channel logos, event artwork, and
thumbnails when available and permitted. - Never invent a broadcaster
logo or use a random image as if it were an official channel logo.

Responsive behaviour: - Design mobile-first. - Support Android phones,
tablets, laptops, desktops, and modern browsers. - On mobile, use a
compact header and a convenient bottom navigation if appropriate. - On
desktop, use a clean horizontal navigation. - Keep the player usable in
portrait and landscape layouts. - Prevent horizontal overflow. - Make
touch targets comfortable on mobile.

Accessibility: - Use semantic HTML. - Provide accessible labels for
icon-only buttons. - Ensure readable contrast. - Support keyboard
navigation for important controls. - Do not communicate status using
color alone.

===================================================================== 3.
PUBLIC HOMEPAGE / DASHBOARD
=====================================================================

The homepage must immediately communicate what is live and make it easy
to start watching.

3.1 Header / navigation Include: - तपाईंको TV logo and name. - Home. -
Live TV. - Sports. - News. - Entertainment. - Search. - Theme toggle, if
implemented. - No viewer login, account, or registration button.

Keep navigation simple. Hide less important links inside a compact
mobile menu.

3.2 Featured priority event — most important homepage feature Create a
prominent featured event section near the top of the homepage.

This section is controlled entirely by the administrator through
Firebase or the selected backend. The administrator must be able to
change the event without modifying frontend source code or rebuilding
the website.

Each featured event should support: - Unique event ID. - Event title. -
Subtitle. - Short description. - Banner image or thumbnail. - Optional
event logo or tournament name. - Associated channel. - Optional
event-specific stream URL override. - Event date. - Start time. - End
time, if applicable. - Time zone configuration; use Nepal Time
(Asia/Kathmandu) for Nepal-focused schedules unless an event specifies
otherwise. - Status: UPCOMING, LIVE, ENDED, or CANCELLED. - Priority
number. - Active/inactive state. - Published/draft state. - Custom
button label, such as Watch Live, Watch Now, or View Details. - Optional
destination URL or internal event page.

Display rules: - Show the highest-priority eligible published event
first. - A lower priority number should mean higher priority; document
this rule clearly. - If two events have the same priority, use a
deterministic secondary sort, such as start time or most recently
updated. - Only show events that are published and active. - A LIVE
event should show a clear red LIVE badge. - An UPCOMING event should
show its scheduled date and time. - An ENDED or CANCELLED event should
not be presented as currently live. - Do not automatically claim that an
event is live merely because its scheduled start time has passed. Use an
explicit admin status or a clearly documented scheduling rule. - If no
eligible featured event exists, gracefully show a default channel
discovery section. - If the event image is missing, use a neutral
designed fallback rather than a random unrelated image. - The featured
button must open the correct event or channel player.

3.3 Multiple featured events - Support more than one featured event. -
Allow the administrator to assign priority values. - Optionally support
a small carousel only when multiple featured events genuinely need it. -
Do not autoplay a carousel aggressively. - Provide clear manual
navigation and accessible controls. - On mobile, keep the primary
featured event readable and actionable.

3.4 Popular channels Display a responsive grid or horizontal row of
popular channels. Each channel item may show: - Channel logo. - Channel
name. - Category. - Country or language, where useful. - LIVE or
availability status only when verified. - Favorite control.

Clicking a channel opens its player page or player view.

3.5 Continue watching / recently watched - Store recently watched
channel IDs locally. - Display a compact recently watched section when
history exists. - Allow users to clear their local history. - Do not
store sensitive viewing information on a server. - If there is no
history, hide the section rather than showing fake entries.

3.6 Sports and special events Create a section for sports and special
events: - Cricket. - Football. - Other sports. - Tournaments. - Special
broadcasts.

Show live and upcoming events based on published backend data. Allow
administrators to prioritize a match or tournament. Do not display
fabricated scores, fixtures, or match statuses.

3.7 Browse by category Support categories such as: - Nepali TV. -
Sports. - News. - Entertainment. - Movies. - Music. - International. -
Regional TV. - Kids and family, only where appropriate and licensed.

Only show categories that contain active, published channels. The
administrator must be able to create, edit, reorder, and disable
categories.

3.8 Announcements Allow the administrator to publish a small
announcement banner. Examples: - A special event is starting soon. - A
channel has moved to a new stream. - Temporary maintenance notice.

Announcements must be dismissible where appropriate and must not
dominate the homepage.

===================================================================== 4.
LIVE TV PLAYER
=====================================================================

Build a stable, responsive video player using established open-source
technologies.

Preferred: - hls.js for HLS playback in browsers that do not support HLS
natively. - Native HTML5 video where supported. - Video.js may be used
if it provides a clear benefit, but avoid unnecessary overlapping player
libraries. - Add MPEG-DASH support only if a compatible playback library
is implemented and tested.

Player requirements: - HLS .m3u8 support. - MPEG-DASH .mpd support if
implemented. - Automatic quality selection when the stream provides
multiple renditions. - Manual quality selection when available. -
Fullscreen. - Volume control. - Mute/unmute. - Play/pause where
supported by the stream. - Loading indicator. - Buffering indicator. -
Playback error handling. - Reconnection with sensible retry limits. -
Responsive player sizing. - Picture-in-picture where supported by the
browser. - Optional playback speed only where the stream and player
support it. - Channel switching without unnecessarily reloading the
whole application. - Clear channel title and logo near the player. - A
useful offline/unavailable message. - A retry button. - A way to return
to channels.

Streaming details: - Detect whether the browser supports the stream
format. - Handle CORS errors, network errors, manifest errors, and
unsupported formats with understandable messages. - Do not retry
endlessly. - Use exponential backoff or a sensible capped retry
policy. - Clean up player instances and event listeners when switching
channels or leaving a page. - Do not create multiple simultaneous player
instances. - Do not autoplay with sound. Respect browser autoplay
restrictions. - Do not promise that a stream is working until playback
has actually been tested. - Do not falsely show a LIVE status based only
on a URL existing in the database.

Quality selection: - Show only quality levels actually exposed by the
stream. - If the stream provides adaptive HLS renditions, support Auto
and the available quality options. - Do not claim that JavaScript can
magically create higher-quality source video from a low-quality
stream. - Do not claim that the application can reduce the broadcaster’s
bandwidth or transcode a stream unless a real server-side transcoding
service exists. - Explain unavailable quality controls gracefully.

Player page layout: - Main video player. - Channel name and logo. - LIVE
or stream status where verified. - Favorite button. - Share button. -
Related channels or next channels. - Optional event details. - On
mobile, keep the player prominent and controls accessible.

===================================================================== 5.
OPEN-SOURCE CHANNEL DATA AND IPTV REPOSITORIES
=====================================================================

Use publicly available IPTV repositories as optional sources for channel
metadata and stream discovery.

Repositories to evaluate: - https://github.com/iptv-org/iptv -
https://github.com/iptv-org/database -
https://github.com/iptv-org/iptv-org.github.io

Use their current documented formats, data files, APIs, and licensing
terms. Verify the current repository structure before integrating it; do
not assume a file path or API endpoint will remain unchanged.

Requirements: - Import channel metadata where permitted. - Organize
channels by country, category, and language. - Display channel name,
logo, country, language, and category when metadata exists. - Allow
administrators to approve or reject imported channels. - Allow
administrators to add custom channels. - Allow administrators to edit
channel metadata. - Allow administrators to disable unavailable
channels. - Allow administrators to remove entries. - Validate stream
URLs before publishing. - Clearly distinguish imported data from
manually verified channels. - Do not assume every listed stream is
operational. - Do not copy or redistribute streams unless the source
license and broadcaster permissions allow it. - Respect repository
licenses, broadcaster copyright, territorial restrictions, and terms of
use. - Do not bypass DRM, authentication, paywalls, geo-restrictions, or
other access controls. - Do not use pirated or unauthorized streams. -
Do not scrape websites in violation of their terms.

Important architecture rule: Do not hardcode a huge channel list in the
frontend. Channel data must come from the backend or a controlled
data-import process.

Create an import workflow: 1. Administrator starts an import. 2. Backend
or trusted import process retrieves permitted metadata. 3. Imported
records are stored as pending/unpublished. 4. Administrator reviews
channel details and stream source. 5. Administrator tests or verifies
the stream. 6. Administrator approves and publishes the channel. 7.
Public website displays only active, published channels.

If an external repository becomes unavailable, the application should
continue using its already stored approved channel records.

===================================================================== 6.
BACKEND ARCHITECTURE — FIREBASE PREFERRED
=====================================================================

Preferred backend: - Firebase Firestore for application data. - Firebase
Authentication for administrator authentication only. - Firebase Storage
for logos and banners. - Firebase Security Rules for access control. -
Optional Cloud Functions for trusted server-side tasks.

The public frontend must not require viewer authentication.

6.1 Public read access Allow unauthenticated visitors to read only
published public data: - Active published channels. - Active published
categories. - Published featured events. - Public announcements. -
Public application settings that are safe to expose.

Do not expose: - Admin account details. - Private configuration. -
Secret keys. - Internal moderation notes. - Draft or unpublished
content. - Private operational data. - Service account credentials.

6.2 Admin write access Only authenticated and authorized administrators
may: - Create, edit, publish, unpublish, or delete channels. - Change
stream URLs. - Create and manage events. - Change priority values. -
Upload or delete approved media. - Manage categories. - Edit public
announcements. - Change public settings. - Enable maintenance mode.

Use role-based authorization. Prefer custom claims or a trusted
admin-role collection whose permissions cannot be granted by an ordinary
user.

6.3 Firebase Security Rules Create and include complete Firestore and
Storage Security Rules.

Rules must: - Permit unauthenticated read access only to explicitly
public published records. - Deny unauthenticated writes. - Deny all
writes from non-admin authenticated users. - Protect unpublished and
draft records. - Validate allowed fields and data types where
practical. - Prevent users from assigning themselves admin privileges. -
Protect uploaded media from unauthorized writes and deletions. - Default
to deny when no rule explicitly allows an operation.

Do not use permissive development rules such as allow read, write: if
true in the final application.

6.4 Firebase credentials and secrets - Frontend Firebase configuration
values may be public identifiers, but they are not authorization. -
Never expose Firebase Admin SDK credentials, service account JSON,
private API secrets, or privileged tokens in frontend code. - Use
environment variables for deployment configuration. - Use trusted
server-side functions for privileged operations. - Include a
.env.example file with placeholder values only.

15. STREAM VALIDATION AND LEGAL RESPONSIBILITY
=====================================================================

The platform must use streams that the operator is authorized to
display.

-   Use publicly accessible streams only when their publication and
    redistribution are permitted.
-   Respect broadcaster copyright, repository licenses, territorial
    restrictions, and terms of service.
-   Do not bypass DRM, login walls, paywalls, geo-blocking, or access
    controls.
-   Do not represent unauthorized streams as official.
-   Keep source attribution or licensing notes where required.
-   Provide an admin-controlled way to remove a stream following a
    rights complaint.
-   Do not fabricate channel logos, broadcaster names, schedules, match
    information, or stream availability.

Technical caveats: - A browser may be unable to play a stream because of
CORS, codec, DRM, network, or browser restrictions. - A URL returning a
successful HTTP response does not guarantee that browser playback will
work. - Some HLS sources may not expose multiple quality levels. - The
website cannot create genuine higher-quality video from a low-quality
source. - Client-side JavaScript cannot guarantee bandwidth reduction or
server-side transcoding. - Do not proxy streams through an unapproved
service or expose private source credentials.

19. FINAL DESIGN AND PRODUCT RULES
=====================================================================

The final application must follow these non-negotiable rules:

1.  The application name is exactly: तपाईंको TV.
2.  Public viewers never need to log in.
3.  Only authorized administrators need to log in.
4.  No public user registration or subscription system.
5.  The featured event is controlled dynamically by the admin.
6.  The highest-priority eligible event appears first.
7.  Channels are managed through the backend, not hardcoded into the
    frontend.
8.  The player must handle errors honestly.
9.  Use open-source technologies and properly permitted channel sources.
10. Never expose privileged credentials.
11. Do not fabricate streams, channels, schedules, or statistics.
12. Keep the interface minimalist, polished, fast, and mobile-friendly.
13. Do not add unnecessary AI-generated design patterns or decorative
    clutter.
14. Build working functionality rather than a static mockup.
15. Document anything that requires external credentials or manual
    setup.

FINAL PRODUCT VISION

तपाईंको TV should feel like opening a television, not opening a
complicated website.

A visitor opens the homepage and immediately sees the most important
live event. They tap Watch Live, choose a channel, and start watching.
No registration, no account, no unnecessary steps.

The administrator opens /admin/login, signs in securely, updates the
featured match, changes a channel stream, uploads a banner, or publishes
an announcement. The public website reflects those changes automatically
without requiring a code edit or redeployment.

Keep the viewer experience effortless and the administrator experience
powerful.

Build a beautiful, reliable, maintainable, and genuinely usable
streaming platform.
